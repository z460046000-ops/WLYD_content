## 两类全景的内容任务

- **业务架构全景**：谁参与、业务如何运转、怎样回应问题并形成结果。角色、业务域、端到端流程、上下游协作、管理执行、共用支撑等只是维度示例，可组合、自建、合并或省略。
- **产品功能全景**：哪些产品模块支撑上述业务、功能如何协同、能力归属和状态是什么。业务应用、功能、入口、共用能力、平台集成、运行支撑等同样不是固定五层。
- 每个核心模块解释“对应问题→使用者与业务动作→支撑能力→产出及价值机制”。若使用看板，说明它帮助看清哪些状态与判断什么；若使用预警，说明条件、异常与跟进责任，不能从名称推定预测或自动处置能力。
- 同组分类口径与颗粒度一致。包含归类、流程顺序、数据交换、依赖与能力支撑分别说明；同组模块不代表完全独立，位置不证明依赖。
- 两图与后文共用 `problemIds`、`capabilityIds`、`scenarioIds`。这些 ID 说明建议组织关系，语义和事实支持仍需复核。

## 如何执行

1. 共享规划接收两份全景规则，先盘点材料，再在 `chapterGuidance[].organization` 保存目标 `purpose`、范围 `scope`、自选 `dimensions` 和理由 `reason`。
2. 四路章节流水线沿用同一版规划与全部原始证据；每章仍单独提取、撰写与校验。全景选择依据缺失时提醒核对，继续按材料生成。
3. 各章完成后，有已完成全景和场景章才执行一次 `panorama-enrichment`。一次请求同时检查已有两图，查看实际场景及其他正文；覆盖充分可不追加。失败的全景章不在此阶段重新生成。
4. 只追加必要上级节点、关键支撑或价值解释，不改原段落、目录、组织维度或共享 ID。逐段检查引文、数字、候选、能力边界、共享 ID 和重复正文，合法部分可以保留。
5. 原稿仍为 `chapters/<key>/chapter.json`；有有效追加时写 `enriched.json`，运行指针指向新文件。根目录 `panorama-enrichment.json` 保存本轮结果、模型建议、过滤原因与覆盖提示。失败保留原稿，不循环重试；取消保留已完成文件并停止后续生成。
6. 对补充后的正文重新计算篇幅、组稿关联，并进行合稿模型复核。ID 覆盖不足只列 `reviewItems`，不因关联不足阻断组稿，也不自动认定语义缺失。

## 能力状态与兼容性

- `plan.capabilities[]` 与全景段落可记录 `capabilityStatus`：`existing`、`pilot`、`planned`、`proposed`、`unknown`。
- `capabilityOwnership` 为 `self`、`third-party`、`customer` 或 `unknown`。缺省保持未知，候选段默认建议状态；不会默认自研或现成功能。
- 全景段落缺标签时可从引用的共享能力保守推导；已知规划/试点/建议不允许显式升级为已具备，已知外部能力不允许显式声明自有。第三方、客户已有、试点、规划有可读标签，仍需正文说明适用边界。
- 同段概述不同能力状态或归属时，整体标签保守记为 unknown 并提示逐项核对；以现有能力提出待确认的流程建议可保留，不能把流程推演与功能状态混为一谈。否定性边界说明不作为正向能力承诺。
- 校验能拦截元数据与部分明确措辞冲突，不能从逐字引文自动证明能力分类或语义正确；模型贴错标签、暗含承诺或不恰当价值归因仍需审核。
- 五个工具参数、章节 key/roleId 和 `report.json` 的主体结构保持兼容；schemaVersion 仍为 2，新增字段为附加信息。全景仍输出文字底稿，不输出可编辑图形节点协议。
