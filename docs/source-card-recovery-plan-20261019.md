# 0.10.1 来源编号与章节恢复修复方案

日期：2026-10-19。状态：用户已确认“修复、打包并更新3081”，已按以下范围实施并部署3081，真实新稿质量及耗时待验收。源码、测试、安装结果以 [测试记录](test-record.md) 为准；本方案本身不代表真实组稿已通过。

## 要解决的问题

0.10.0 实测首稿只有 1/9 章有正文。报告所列失败链路可在源码中对应：模型将知识库证据编号 `K…` 填入 `sourceCardIds`，程序只接受本批原文卡编号 `s-…`，事实因此被排除；落盘的空 `cards.json` 又阻断章节修订的非空卡池回退。部分原始材料其实存在，不能将这类程序故障都报为用户缺料。

演示层另有两个问题：句段编号顺序不同会整批回退原文分页；`retry=true` 仍复用旧的精简计划，不能真正重新提炼。修复应保住已有 MD/DOCX 和原文来源，不把演示错误放大成整篇交付失败。

证据口径：

- `draftWritePrompt` 已从模型输入中剔除 `evidence`，但仍暴露 `sourceEvidenceId`，且未明确 `sourceCardIds` 取顶层 `id`。不能据此断言实际提示词同时暴露三个编号、模型“按多数选择”。
- 4186 字符请求发生超时只能确认该请求失败，不能据此认定批次过大或推断真实耗时根因。
- 报告中 0.7.0 的章节失败与本次是否同根因，尚无同级原始证据证明；本次不将历史失败全部归为同一问题。

## 主要风险与人工验收

1. 同一 `K…` 可能对应多张切片卡；必须限制为当前批次并按原文核对，不能猜选片段。
2. 恢复不得复活已被用途规则拒绝的内部材料、无授权案例或无据资质；先恢复编号，再走现有事实与段落校验。
3. 补写与章节修订都要保留旧版本；卡池恢复成功不等于正文获业务确认。
4. 演示重排只处理合法编号的原文次序，不能借容错漏掉条件或让原句产生新含义。显式重试会增加一次输出阶段的模型耗时。
5. 自动化与安装检查不能替代真实 CallWan 方案验收。更新后重点人工核对正文覆盖、案例缺失标识、事实引用与能力边界、单章修订、HTML 重试，以及实际耗时和模型请求数。
