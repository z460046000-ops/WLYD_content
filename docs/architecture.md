# 产品架构与调度边界

## 本版已实现

`输入文件/会话附件 → 逐文件转换 → 唯一授权目标时上传 → 查询解析状态 → 授权材料目录与全局发现 → 共享主线 → 逐章检索/提取/补查/撰写 → 引文检查与合稿复核 → 报告待人工确认`。

每次导入或生成都有独立 `runId` 和私有运行目录。`run.json` 记录状态与可信会话身份（可得时）；规则加载时记录每个文件的版本和实际 SHA-256，组合成规则指纹。后端文档的 `pending`/`processing` 不进入检索；检索仅用当前配置账号可见且绑定到项目的知识库。

DSH 提供通用对话界面与模型服务，`src/index.js` 注册官方工具，`src/workflow.js` 负责阶段编排，`src/convert.js` 与 `src/platform.js` 分别适配文件和内容中台，`src/retrieval.js` 管理本次运行的查询、原文和章节选材，`src/rules.js` 读取规则。开发目录、安装到 profile 的插件包、会话工作区产物是三个独立位置，详见 README 的位置表。

会话附件须匹配用户真实上传引用；可恢复模型省略的 `sha256:` 前缀，实际读取始终使用会话中的可信引用。目标项目与绑定库核对后，查询库内文档；后台 `file_hash`（MD5）和文件大小一致时复用已有文档 ID。本地来源另存 SHA-256。该处理避免相同材料重复上传，不把 HTTP 500 解释为成功。

## 内容结构

- `rules/templates/presales-solution.json` 是“产品售前解决方案”的默认目录。六章仅适用于该方案类型；合作案例可选，其他章资料不足时保留缺口。
- 用户在 DSH 对话中提出增删、改名、排序等调整。目录工具检查稳定 `key`、语义 `roleId` 和自定义章节要求，先展示预览。当前用户确认发生在对话层，尚未提供持久化的目录版本审批界面。
- `rules/chapters/*.json` 按章节角色定义提取问题、撰写方式、校验和缺失处理。章节规则不按第几章绑定，所以可以换序和复用。新方案类型需要新增模板；“客户解决方案”的真实目录须由用户提供。
- 全篇 goodcase 扫描发现实施与服务保障可单列；本版提供 `delivery-service` 可选角色，但不改动已确认的六章默认目录。
- `rules/global.json` 与 `rules/style.json` 为所有方案共用。它们不包含客户、能力、数字等事实；goodcase 仅用于提炼组织方法。
- 隐藏组稿顺序是“有据能力→可用场景→回应的问题→相关趋势”；展示顺序仍以用户确认的目录为准。先检索本次材料与授权知识库；缺直接关系时，保留清楚标为“待确认”的典型场景假设或建设方向。`assemblyLinks` 保存能力引文与正文段落的建议关系，`reviewItems` 提醒人工核对；缺关联本身不进入 `gaps`，也不阻断生成。
- 已核对的事实段须逐字引文；待确认候选只表达建议，不宣称客户已发生问题、产品已实现能力或真实政策。当前机器只能校验引文和编号，无法自动证明语义关系成立。
- `extractQuestions` 是重点检索提示，不是材料白名单。查询还结合章节目标、受众、共享计划和业务术语。全部已读本地材料与已召回原文存档；每次模型调用选择相关完整片段，不截取前几百字充当原文，也不把存档全集反复传给所有阶段。条数选择仍可能遗漏关键内容，不能声称覆盖全库。超出真实模型上下文时明确报错，不静默裁剪。
- 单文件入口上限 500 MB，逐个读取与转换；上传时从落盘 Markdown 构造文件流。ZIP 展开总量仍有防压缩炸弹上限。解析器内存、DSH 附件入口、内容中台请求体及模型上下文各有独立边界，真实 500 MB 链路待联调。

## 按章节取证

`0.3.0` 的 `createRetrieval` 是运行内的证据管理入口，职责与 HTTP 接口分开：

| 阶段 | 输入与行为 | 保存内容 |
|---|---|---|
| 准备 | 校验项目、绑定库和可见库，读取解析完成文档；本次运行只准备一次 | 材料目录、可用库及覆盖状态 |
| 发现 | 通过全局能力/场景和问题/趋势查询、本地代表片段建立材料认识 | 完整命中与发现查询，不把摘要当原始证据 |
| 规划 | 以材料目录、代表证据和规则建立能力→场景→问题→趋势主线 | `plan.json`，含章节指导与动态查询 |
| 逐章取证 | 按 `chapterKey` 查询；选择本章命中、相关共享主线原文及本地片段 | `chapters/<key>/retrieval.json` |
| 补查 | 提取发现具体不足时，最多一轮新查询并刷新提取结果 | 补充查询、追加原文和结果；仍缺则待确认 |
| 后续生成 | 撰写使用本章证据；全景使用相关章节材料；最终复核使用全文及实际引用/主线原文 | 正文、复核结果；机器引文检查仍使用完整证据登记 |

同一 `roleId` 可对应多个 `chapterKey`，章节改名或换序不会改变取材归属。查询显式携带用途、章节和角色，公共查询缓存保留各章归属。知识证据按知识库、文档、块及内容摘要生成稳定 ID；重复命中合并召回原因，原文不被后一次查询覆盖。缓存仅限本次运行，证据与审计快照依序落盘，避免并发章节互相覆盖。

本地材料按标题、词面匹配和相邻段落选择；这是轻量选段，不是语义向量检索。后台优先复用 `retrieval/query` 的 hybrid 原文，只有路由返回 404/405 才明示回退旧 `hybrid-search`；授权失败不回退。每次请求都带已授权的完成文档 ID，没有完成文档就跳过，不能传空列表扩大成全库查询。响应的来源状态、局部失败和 traceId 进入审计记录。

Wiki/图谱未加入正文取材；过滤范围、源引用回读和图谱库级语义待联调。后台父块/邻块原文读取也未接通；保存返回的定位信息，使用完整命中块和定向补查补充上下文。没有可靠原文时明确待确认，不生成伪造的“上下文”。

## 模型与章节调度

当前 `src/workflow.js` 是 DSH 工具驱动的确定性阶段入口。平台未来可按阶段状态调用同一能力：`convert`、`upload`、`readiness`、`retrieve`、`assemble`、`validate`、`publish`。若扩展为海报等内容产品，可复用材料、证据与事实校验阶段，另加新的内容模板和呈现适配器。HTML、PPTX、PDF 不进入本版，也不把旧插件或 HTML Anything 作为运行时依赖。

`src/generation.js` 先形成共享能力与问题关联计划，再调度最多八条逐章取证→提取→按需补查→撰写→校验流水线。各章拿到证据后即可继续，共享计划在运行内固定。按目录合稿后，通过 `src/panorama.js` 最多一轮按需追加两类全景，再做只审核、不重写的模型复核。`src/scheduler.js` 提供进程内默认八路、可配置 1–12 路额度与取消。模型请求共享八路名额，后台检索共享四路名额；多个生成运行也共享额度。`dependsOnRoles` 是语义依赖，不直接决定拓扑排序。

`src/model.js` 在运行开始时优先读取 `agent.session.requestHeader().config`，无有效路由时回退 `agent.options`，固定本次运行的 provider/model/reasoningEffort，避免前端切换模型后仍使用旧 Agent 配置。思考强度原样透传，不自动降档。默认排队最多 30 分钟，获得名额后执行最多 10 分钟，分别配置并计时。`WLYD_ASSEMBLY_STAGE_TIMEOUT_MS` 是按阶段的毫秒 JSON 对象，`WLYD_ASSEMBLY_QUEUE_TIMEOUT_MS` 控制排队，两者有效范围均为 60 秒至 30 分钟；详见 README。取消信号同时约束排队和执行。

规划保存在 `plan.json`，逐章保存在 `chapters/<key>/`，根 `retrieval.json` 保存查询审计，`evidence.json` 保存完整原文。`run.json.chapters` 记录状态与尝试次数，`modelRequests` 记录实际请求规模、模型路由和阶段结果：入队、发起、首个思考/文本事件、首个文本、结束、排队/执行耗时，以及提供方返回的 usage。UTF-16 字符长度、UTF-8 字节数和 token 分开，usage 未返回就保留空值。

提取/撰写各最多两次，具体缺项可另触发一轮补查，有新证据才刷新提取结果；单章失败保留其他结果。规划失败明确记录降级并进入工具摘要。JSON 只做保守格式修复；截断或不确定的响应仍报错。检测到上下文超限时不自动裁剪或重试同一请求；整稿复核超限则改为逐章和相关场景分组审核，失败范围单独记录在 `consistency-review.json`，不会假称已完成语义检查。状态查询由调用方触发：生成状态只读，导入状态仅变化时写盘。没有跨进程自动恢复、单章对话重写或多人审批状态机。

`generate` 工具返回精简且可直接序列化的摘要，完整状态仍落盘。正文共用写法优先短标题、短语概括和短句解释；输入证据保持完整，校验仍逐字定位引文，不以写法偏好代替事实审查。

业务章在现状/挑战间二选一，趋势章在 PEST/管理业务技术间二选一；用户参数优先，auto 在规划时选择并记录理由。LLM 为各节点生成语义相近的展示标题，`canonicalTitle`、key、roleId 保留，避免标题变化破坏规则绑定。业务分析正文占比 15–30%、解决方案及子章合计 40–60% 是软目标，结果不足只提醒。规则纪律限制无据政策、数字和能力，不为比例凑字数。

`needs_human_review` 只代表合稿和落盘完成，不保证六章均合格，也不保证对外受众适配。旧版浏览器报告保留了 20 处有效逐字引文，但跨章关联记录未通过，正文还含内部研发和商业判断；新版增加了受众规则和共享规划，真实质量是否改善仍待业务材料复验。

要把目录编辑做成多人协作功能，还需后端提供目录实例 ID、版本号、乐观锁和审批事件；当前本地 JSON 预览不能代替该平台能力。

后续优先验证逐章取证是否遗漏关键材料，以及实际输入和耗时是否改善，再接原文回读、Wiki/图谱、单章版本与恢复。八路与六路比较、降低思考强度、合并提取与撰写只在计时支持明确假设时分别验证，不能把未做的实测写成性能收益。见 [后续待办](backlog.md) 与 [测试记录](test-record.md)。

## 两类全景的动态组织与补充

共享规划先接收两份全景章节规则，在 chapterGuidance.organization 记录目标、范围、自选维度与理由；八路章节任务共用规划。业务全景解释业务运转，产品全景解释功能支撑，读者、问题和重点场景决定组织方式，不固定层级。两图与后文共用问题/能力/场景 ID。

各章完成后，仅在有成功全景章与场景章时进入 enriching_panoramas；一次模型请求同时核对现有全景，只追加必要上级节点、关键支撑或价值说明。重复、目录外、无效来源、无据数字及已知能力升级冲突的新增段落过滤；失败保留原稿。原 chapter.json 保留，有追加时另存 enriched.json 并更新运行指针，根 panorama-enrichment.json 保存结果。重新计算最终篇幅和关联再做合稿复核；ID 覆盖只作待核对提示，不替代语义判断。

能力状态和归属附加在共享能力与全景段落：未知保持未知，已知试点/规划/第三方/客户已有不能显式升级成全面具备/自研。具体边界仍需语义审核。工具参数和报告主体兼容；内容生成不是自动绘图或微调训练。规则依据见 [全景学习记录](panorama-rule-evidence.md)。
