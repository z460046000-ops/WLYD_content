# 产品架构与调度边界

源码基线：0.10.0，全局规则 0.11.0。本轮合并宏观规划、合并章内提写、精简查询、先交初稿再复核；保留知识库真实取材、确认和关联必检。按用户要求未安装或重启DSH，3081上次安装记录为0.8.0。验证边界见 [测试记录](test-record.md)，完整入口、配置和路径见 [README](../README.md)。

## 0.10.0 文案与多格式输出

`report.json`继续作为可编辑文案主记录；`src/content/snapshot.js`投影出无版式的固定版本，保留目录、段落ID、来源、主线、能力条件及确认/审核状态。`coverage.js`单独计算有正文节点与材料卡，并记录未成稿原因。正文或来源/版本/确认变化使输出源哈希失效；主题变化不影响文案哈希。

`outputs/markdown.js`与`docx.js`是确定性文档适配，不调用模型。`outputs/html-slides/plan.js`在文档发布后按章分批选择原文关键句，程序映射出处与主线并保留条件；非法ID、漏条件或模型失败时明确降级为原文分页。`render.js`固定模板转义正文，内嵌真实上游引擎，不执行模型生成的任意JS。`prompts/outputs/`、`vendor/xiaoma-studio/`只在输出阶段读取，未耦合到`rules/chapters`。

`delivery/tasks.js`先写完整文档、快照和manifest后公布路径，再启动独立宿主job。文案job返回文档及HTML jobId；HTML失败/取消不会改变文案任务结果或删除文档。每个exportId独立目录，最新指针只在提交时前移；旧作业结束不改新指针，当前文案改变则旧作业和query均标stale。导出前验证当前用户、材料摘要、知识授权和每条引用；HTML发布前再查权限。缺归档拒绝导出。

`orchestration/status.js`只改变模型侧状态渲染：默认摘要/正文覆盖与有限差异，原始run和modelRequests保留用于显式详情。`skills/wlyd-assembly-orchestrate`与小段工具引导复用DSH现有完成通知和job_output等待，未改DSH核心或profile。`routes.js`允许写作、演示角色独立于编排会话选择模型；没有配置时维持原行为，不擅自切换用户路由。仅复用有效已确认planId，没有新增自动规划缓存。

新增文件与API、交付时序、扩展海报/视频的方法见[输出使用说明](output-guide.md)。现有Markdown报告视图继续兼容，未为拆层搬动整套旧模块；新输出只读快照。

## 0.9.0 默认快稿与章节迭代

`generate` 的公开入口默认 draft，tasks 将质量模式写入输入、去重键和检查点；strict 明确指定。`generation.js` 路由至 `draft-generation.js` 或原严格流水线。快稿每章一条主查询，成功但空或明显过少再补一条；同一次模型调用归纳事实与写正文。长材料每窗2400字符、重叠160、每批最多8000字符，处理所有选中窗口。续写仅带最近八段各120字符摘要，防历史上下文增长。

`planning.js` 将宏观归纳与大纲合为一次请求：最多四条知识片段，每条开头1800字符；事实和主线引用只对本次送入选段核对。没有有效宏观事实时，用明确标为未概括的原文锚点继续粗规划；知识库零命中仍不创建可确认版本。完整来源独立留档。

`combined-writing.js` 生成稳定原文卡 `s-*`；模型同次返回简短facts和正文factIds，程序仅允许当前批原文卡、核对来源与用途，再生成兼容旧改单章的 `f-*` 卡库。`fact-cards.js` 补引文、标注待验证。模型分类是自报口径，不是独立语义证明。中断只恢复sections中的完整正文，不把facts.text当正文。无事实的企业/案例章输出needs_input材料卡；standard最多修正一次，strict沿原路径。

每章完成由 `onDraft` 串行发布：先写evidence、report和review视图，再在run中公开路径与reportReady。`draft_building`表示逐章出稿，`draft_reviewing`表示全章产物已交、关联复核继续；firstChapterReadyAt/draftReadyAt/reviewFinishedAt区分三个时点。宿主job、claim和心跳持续到复核结束，初稿可读不等于作业已完成。取消或失败保留已交文件并标未完成复核。复核只一轮、不自动修复；输入段落不重复整窗引文，来源选段仍完整去重送检。

`chapters.js` 管理评论、追问、解决和章节版本。初稿发布且job活跃时只允许list；其他动作等待结束，或取消并等锁释放后操作，防旧复核覆盖新稿。revise重新核对材料摘要和知识库授权，复用本章卡库，只替换目标章或目标段。run锁与expected_version防并发覆盖；保留版本，report.json为主记录，其余为视图。修改后复用不变检查；人工approve与机器核验独立。没有多文件事务，磁盘或进程在写视图时失败可能需刷新恢复。

以下严格批次和修复说明继续作为 strict 的实现细节；draft 的状态是 draft_ready，章节为 draft_unverified 或 needs_input。

## 阶段与用户确认

```text
导入同步到项目知识库或选择已有知识库
→ outline action=plan：知识库真实命中、粗目录、少量主线
→ 展示给用户
→ outline action=confirm：真实 plan_id + plan_sha256
→ generate mode=start：校验、去重、接纳后台作业、返回 runId
→ draft/standard各章：定向查询→同次归纳事实和写作→逐章刷新初稿
→ 全章产物可读，宿主任务继续完整段落与关联必检
→ 检查结束，逐章迭代；strict继续原提取、修正与复查流程
```

`action=preview` 只是模板预览，不能拿来生成。规划只取最多四条代表性证据，粗目录每章说明目的、检索方向，能力→场景→问题→趋势只挑少量主线，不在规划期穷举全功能或设计详细全景。

确认固定目录、作者/领域/目标/读者、材料和规则版本。生成必须校验真实确认记录和哈希，显式传目录也不能绕过。用户确认意图仍由 DSH 对话入口负责，本地布尔字段不能证明真人审批或多人授权。

规划必须取得当前项目授权知识库的真实片段命中，本地导入材料不能替代宏观命中创建确认版本。能力、场景、问题和趋势保留来源与候选身份，不把厂商自身问题变成客户问题；候选不能升级已有或自有。内部规划话术不进入标题和正文。全局规则0.11.0改变指纹，以后安装0.9.0后须重新plan/confirm，已有导入材料可复用。

## 作业生命周期、去重与恢复

`generate` 不等待整篇成稿。校验通过后通过 DSH `jobs` 托管，保存 `run-input.json` 和运行状态，再返回 runId；`status` 读取进度，`cancel` 通过宿主会话授权取消。后台任务绑定所属会话和宿主生命周期，插件卸载会中止；关电脑后不会继续。

同工作区内，项目、材料、确认规划、规则、模型等相同输入复用已有任务。`.requests/` 为稳定接纳索引，`.claims/` 为占用、租期和历史记录；它们不是远程队列。显式 `mode=regenerate` 创建新运行，保留旧产物。

进程退出后，查询可报告 `interrupted`；用户显式调用 `mode=resume`、提供原 `run_id` 才接续。恢复重新核对确认版本、材料内容、规则、目录、固定模型与当前权限。章级 `checkpoint.json` 绑定证据、事实卡和正文指纹；完成章通过原文及机器校验后复用，有效提取阶段可接续写作，其余只处理未完成部分。模型请求历史按恢复次数追加，待完成请求标中断。

部分成功为 `partial_draft`，所需正文节点完整后仍是 `needs_human_review`；全部零正文为 `failed`，也保存带确认目录的 `report.md` 与独立审核，后台作业保持失败状态，可沿原 runId 恢复。取消和中断单列。`chapterOutcomes` 区分 completed、partial、failed、omitted，含有效段落的 partial 章仍不完整；显式省略的可选章不当作失败。正文完整与合稿检查通过是两个字段，不能混为一谈。旧版没有新版检查点的运行不可直接恢复。知识文档不可变版本尚未接入，已有哈希与当前权限复核不能替代平台版本管理。

检查点以整章提取、整章成稿为恢复单位；partial 章可复用有效提取，但本章写作会重写，不宣称单独恢复失败批。全景补充也保存输入与结果指纹，只有完整成功且产物、引用和追加边界有效时复用。接纳索引发布前先保存可恢复输入；运行锁以完整目录原子发布，历史记录保留。

## 证据与上下文

模型提示词由三层组成：`global.sharedRules` 保存共用事实、关联、能力和全景原则，`global.stageContracts` 保存当前阶段任务，章节 JSON 保存该角色特有的重点与写法。`prompts.js` 将它们按 `plan/extract/write/panorama-enrichment/consistency-review/relationship-repair` 投影到**每次独立请求**；写作阶段另带 `style.principles`。提取只带 `extractQuestions` 与材料用途字段，撰写只带 `write`、用途和已选模式/框架，全景追加只带角色职责与组织提示；`validate` 等程序规则仍完整加载并参与检查，不再随每个写作批重复发送。

产品能力→场景→客户问题→相关趋势在共用规则中维护，关联 ID 随各章相关主线传递，合稿仍执行五项检查；缩短提示词不删除证据和事实边界。固定九章模拟输入下 31 次请求总序列化字符约减少 24.4%，证据字符量不变；这只是请求规模实验，不能代替真实 token、耗时或内容验收。

统一 `/retrieval/query` 只接 hybrid，限定当前可见项目绑定库和解析完成文档。空授权文档列表不查询全库；只有 404/405 回退旧接口，401/403 不回退。后台 top_k=12，章内选择最多八条远程命中与必要主线锚点，全部已召回原文另存。

正文仅做章节查询，不再全局发现；远程命中后不叠加整批本地副本。每章记录当次查询与命中；零命中时只可用规划中已核准的知识库锚点写待确认草稿，不能把本地材料或旧锚点算成新命中，也不能把该章标完整。候选可能漏召回，不能宣称覆盖全库。

长原文约 2400 字符窗口、160 字符重叠、每批约 6000 字符；所有选定窗口处理到末尾。事实卡保留短逐字引文、条件、否定、时间、归属和状态；撰写只携带本章本批事实、必要原文及相关主线/规则。引文合法不证明概括语义必然准确。

用途识别复用原有 extract 请求，不增加独立的串行分类模型调用。事实卡标注 subject、purpose、topic、supportMode，经全局词表归一化后由章节角色的 `contentPolicy` 筛选，目录名称和层级仍可编辑。原件、命中片段及未选用事实留存，筛选不修改 RAG 库。

客户问题和趋势中，主体或用途未知的内容保持候选身份；企业介绍和案例通过 `requireKnownPurpose=true` 要求明确对应用途，不能用内部目录和“没有材料”的说明填正文。未知标签只是未核验，不证明材料真实、适用或可对外披露；语义判断依赖真实模型和业务审阅。

进入写作前按事实内容与边界去重、合并引用，并以主题组织适中批次，避免各批重复介绍同一论点。同章同类校验问题只做一次局部修正；通过的段落不跟随错误段丢弃，失败批不阻断其他批。章节保留有效正文但仍有失败或未解决过滤时标 partial；没有可用正文则 failed。无正向事实且明确 `required=false` 的章节可 omitted，必需章与失败章仍保留简短占位。编号、引文、数字及能力边界校验保持严格。

generation 将同一正文检查回调交给 panorama/review；全景追加、关联替换及其缓存结果均受本章已路由事实的引用与候选边界限制。拒绝时保留原稿，审核记录具体原因，不让后置修改绕过初稿检查。

补查最多一轮，按内容去重，只提取新增证据。记录问题、新证据与新事实数量，不用数量冒充问题已解决。输入超限可拆当前批，有可见输出的输出耗尽可缩小任务；零正文输出耗尽、排队超时、执行超时、429 不通过拆材料制造请求。

Wiki/图谱、后台父块/邻块回读、公开检索仍未接。引文附近条件窗口可能不足以解释远距离限制，需真实材料检查。

## 全章并行、路由与观测

所有章节进入任务，各章按取证→提取→必要补查→写作推进，取证就绪即可写。模型进程内共享默认八路（1–12），检索独立四路。`WLYD_ASSEMBLY_ROUTE_CONCURRENCY` 为具体 provider/model 或提供方配置更小路由额度；先等路由再占全局额度，避免饱和路由堵住其他模型。

每次运行固定模型。宿主声明支持低档时选 low/minimal/off/none，不继承会话 high/max；缺能力声明时使用提供方默认并记录未验证。默认不设置插件硬编码 maxTokens，显式预算由 `WLYD_ASSEMBLY_OUTPUT_BUDGETS` 配置。路由 defaultMaxTokens 不是模型能力上限。

429 最多退避两次，尊重提供方等待时间并加短抖动；Retry-After 超过 60 秒停止重试。等待释放额度，可取消。独立记录队列时间、服务时间、退避、每次尝试、请求输入、输出/思考字符、结束原因和可得 usage。字符不能当 token，缺 usage 不估算账单。排队默认 30 分钟、执行默认 10 分钟，延长超时不代表提速。

## 必经合稿检查与修正

全部段落进入章节批次；全部业务问题、场景、趋势重点段进入关系批次。按相关章节和主线合批，保留所有共享 ID 的显式目标，补充词面候选。章批通常最多六段/约 8000 字符；关系批最多九段/四条主线/约 11000 字符，导航最多八条。单段长文完整保留，不能把这些组织阈值当硬输入上限或固定 token 限额。

五项必检为问题方案、能力证据、场景全景、趋势建设、矛盾与孤立内容。状态/归属差异先用程序标识，章批仍审核语义。所有 focus 关系必须有可联合检查的目标正文，未知或缺目标不得通过；有限词面候选不是语义穷尽证明。

`coverage` 记录段落和重点关系的总量、完成量与未检查 ID。各批及时保存；正文、规则、主线、索引和实际证据选段共同生成指纹，只有指纹一致的已完成检查可复用。失败不冒充成功缓存。

有具体问题最多一轮局部修正，三个组、每组两段；保留 ID、原稿与候选边界。修后重组必要任务，只调用变化或新增批次，未变化批次复用；无变化修正也缓存。联合语义因资源限制拆开时，子批通过不能替代原联合检查通过；缺章、缺项、超时均保留未完成或待审。

## 正文与内部审核

`report.md` 只输出确认目录下的方案正文、来源依据及简短的部分稿/缺章提示，保留章节层级；不追加长篇运行问题、待审项和缺口说明。可选案例被省略时只在内部审核记录原因。

`review.md` / `review.json` 另存内部审阅：相同文本跨类别合并、按章节归组，保留类别、出现次数和原始数组。`report.json` 继续保留正文、章节结果及原始审阅数据，程序去重不销毁原记录。`run.json` 与 status 返回 reviewPath、reviewJsonPath、partial/omitted 章信息；报告与运行状态对齐，不将部分稿标完整。
