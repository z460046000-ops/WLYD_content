# 产品架构与调度边界

## 本版已实现

`输入文件/会话附件 → 逐文件转换 → 唯一授权目标时上传 → 查询解析状态 → 已完成文档 chunk 检索 → 依目录与规则生成 → 逐字引文检查 → 报告待人工确认`。

每次导入或生成都有独立 `runId` 和私有运行目录。`run.json` 记录状态与可信会话身份（可得时）；规则加载时记录每个文件的版本和实际 SHA-256，组合成规则指纹。后端文档的 `pending`/`processing` 不进入检索；检索仅用当前配置账号可见且绑定到项目的知识库。

DSH 提供通用对话界面与模型服务，`src/index.js` 注册官方工具，`src/workflow.js` 负责阶段编排，`src/convert.js` 与 `src/platform.js` 分别适配文件和内容中台，`src/rules.js` 读取规则。开发目录、安装到 profile 的插件包、会话工作区产物是三个独立位置，详见 README 的位置表。

会话附件须匹配用户真实上传引用；可恢复模型省略的 `sha256:` 前缀，实际读取始终使用会话中的可信引用。目标项目与绑定库核对后，查询库内文档；后台 `file_hash`（MD5）和文件大小一致时复用已有文档 ID。本地来源另存 SHA-256。该处理避免相同材料重复上传，不把 HTTP 500 解释为成功。

## 内容结构

- `rules/templates/presales-solution.json` 是“产品售前解决方案”的默认目录。六章仅适用于该方案类型；合作案例可选，其他章资料不足时保留缺口。
- 用户在 DSH 对话中提出增删、改名、排序等调整。目录工具检查稳定 `key`、语义 `roleId` 和自定义章节要求，先展示预览。当前用户确认发生在对话层，尚未提供持久化的目录版本审批界面。
- `rules/chapters/*.json` 按章节角色定义提取问题、撰写方式、校验和缺失处理。章节规则不按第几章绑定，所以可以换序和复用。新方案类型需要新增模板；“客户解决方案”的真实目录须由用户提供。
- 全篇 goodcase 扫描发现实施与服务保障可单列；本版提供 `delivery-service` 可选角色，但不改动已确认的六章默认目录。
- `rules/global.json` 与 `rules/style.json` 为所有方案共用。它们不包含客户、能力、数字等事实；goodcase 仅用于提炼组织方法。
- 隐藏组稿顺序是“有据能力→可用场景→回应的问题→相关趋势”；展示顺序仍以用户确认的目录为准。先检索本次材料与授权知识库；缺直接关系时，保留清楚标为“待确认”的典型场景假设或建设方向。`assemblyLinks` 保存能力引文与正文段落的建议关系，`reviewItems` 提醒人工核对；缺关联本身不进入 `gaps`，也不阻断生成。
- 已核对的事实段须逐字引文；待确认候选只表达建议，不宣称客户已发生问题、产品已实现能力或真实政策。当前机器只能校验引文和编号，无法自动证明语义关系成立。
- `extractQuestions` 是检索提示，不是过滤条件。本次上传材料的可读正文全部分段保留；绑定知识库先做宽泛检索再按章节追问，去重后把命中全文交给模型。插件不做 token 压缩，若超出 DSH 模型上下文，由平台报错；不静默丢弃尾部材料。
- 单文件入口上限 500 MB，逐个读取与转换；上传时从落盘 Markdown 构造文件流。ZIP 展开总量仍有防压缩炸弹上限。解析器内存、DSH 附件入口、内容中台请求体及模型上下文各有独立边界，真实 500 MB 链路待联调。

## 后续调度扩展

当前 `src/workflow.js` 是 DSH 工具驱动的确定性阶段入口。平台未来可按阶段状态调用同一能力：`convert`、`upload`、`readiness`、`retrieve`、`assemble`、`validate`、`publish`。若扩展为海报等内容产品，可复用材料、证据与事实校验阶段，另加新的内容模板和呈现适配器。HTML、PPTX、PDF 不进入本版，也不把旧插件或 HTML Anything 作为运行时依赖。

`0.2.3` 的 `generate` 由 `src/generation.js` 先形成共享能力与问题关联计划，再调度最多八条逐章提取→撰写→校验流水线，按目录顺序合稿，通过 `src/panorama.js` 最多一轮按需追加两类全景，再做只审核、不重写的模型复核。`src/scheduler.js` 提供进程内默认八路、可配置 1–12 路额度与取消，`src/model.js` 负责会话模型/思考强度透传、十分钟超时及保守的 JSON 格式修复，`src/content.js` 负责引文、数字、段落 ID 和 Markdown。提取与撰写共用模型额度，多个生成运行也共享。`dependsOnRoles` 是语义依赖，不直接决定拓扑排序。

规划保存在 `plan.json`，逐章保存在 `chapters/<key>/`，`run.json.chapters` 记录状态与尝试次数，`modelRequests` 记录请求规模与阶段结果。提取/撰写各最多两次，单章失败保留其他结果；取消停止排队并通知活动请求。检测到上下文超限时不自动裁剪或重试同一请求。状态查询由调用方触发：生成状态只读，导入状态仅变化时写盘。没有跨进程自动恢复、单章对话重写或多人审批状态机。

`generate` 工具返回精简且可直接序列化的摘要，完整状态仍落盘。正文共用写法优先短标题、短语概括和短句解释；输入证据保持完整，校验仍逐字定位引文，不以写法偏好代替事实审查。

业务章在现状/挑战间二选一，趋势章在 PEST/管理业务技术间二选一；用户参数优先，auto 在规划时选择并记录理由。LLM 为各节点生成语义相近的展示标题，`canonicalTitle`、key、roleId 保留，避免标题变化破坏规则绑定。业务分析正文占比 15–30%、解决方案及子章合计 40–60% 是软目标，结果不足只提醒。规则纪律限制无据政策、数字和能力，不为比例凑字数。

检索前置阶段最多四路请求，并隔离单查询/单库失败；成功片段按固定请求顺序归并去重。当前还是 hybrid-search，新统一接口的 hybrid/Wiki/图谱归一化、来源回溯和局部状态见 [后续待办](backlog.md)。不能直接把知识库级图谱当业务全景图。

`needs_human_review` 只代表合稿和落盘完成，不保证六章均合格，也不保证对外受众适配。旧版浏览器报告保留了 20 处有效逐字引文，但跨章关联记录未通过，正文还含内部研发和商业判断；新版增加了受众规则和共享规划，真实质量是否改善仍待业务材料复验。

要把目录编辑做成多人协作功能，还需后端提供目录实例 ID、版本号、乐观锁和审批事件；当前本地 JSON 预览不能代替该平台能力。

## 两类全景的动态组织与补充

共享规划先接收两份全景章节规则，在 chapterGuidance.organization 记录目标、范围、自选维度与理由；八路章节任务共用规划。业务全景解释业务运转，产品全景解释功能支撑，读者、问题和重点场景决定组织方式，不固定层级。两图与后文共用问题/能力/场景 ID。

各章完成后，仅在有成功全景章与场景章时进入 enriching_panoramas；一次模型请求同时核对现有全景，只追加必要上级节点、关键支撑或价值说明。重复、目录外、无效来源、无据数字及已知能力升级冲突的新增段落过滤；失败保留原稿。原 chapter.json 保留，有追加时另存 enriched.json 并更新运行指针，根 panorama-enrichment.json 保存结果。重新计算最终篇幅和关联再做合稿复核；ID 覆盖只作待核对提示，不替代语义判断。

能力状态和归属附加在共享能力与全景段落：未知保持未知，已知试点/规划/第三方/客户已有不能显式升级成全面具备/自研。具体边界仍需语义审核。工具参数和报告主体兼容；内容生成不是自动绘图或微调训练。规则依据见 [全景学习记录](panorama-rule-evidence.md)。
