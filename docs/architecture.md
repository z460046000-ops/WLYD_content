# 产品架构与调度边界

源码基线：0.4.0 第一批，尚未打包部署及真实生成验收。完整入口、配置与产物路径见 [README](../README.md)。

## 模块边界

| 层 | 文件 | 职责 |
|---|---|---|
| DSH 入口 | index.js / schema.js | 五个官方工具、标准参数、明确规划与确认协议 |
| 阶段编排 | workflow.js | 导入、查询、只生成已确认版本、成稿落盘 |
| 规划与版本 | planning.js / plan-model.js / store.js | 作者身份与读者分离、粗目录、少量主线、哈希确认和材料路径 |
| 输入与平台 | convert.js / platform.js | 转 Markdown、上传、解析就绪、可见项目和授权库适配 |
| 检索 | retrieval.js | 宏观发现和章节查询分开，登记原文、稳定 ID、查询审计与去重 |
| 阶段上下文 | context.js / facts.js | 共用规则投影、完整证据分批、带来源事实卡、引文附近条件 |
| 内容生成 | generation.js | 全部章节提交并行任务、独立取证、增量补查、分段写作、按目录合稿 |
| 全景补充 | panorama.js | 小范围最多一轮必要追加；超出组织阈值转交关联检查 |
| 合稿必检 | review.js | 五项检查、所有正文覆盖、无共享编号的跨章候选、局部修正并复查 |
| 模型与调度 | model.js / scheduler.js | 固定路由、声明支持的低思考、输出预算、共享八路模型/四路检索、超时与取消 |
| 内容校验 | content.js | 引文、数字、目录、候选与能力边界；Markdown 输出 |
| 规则 | rules.js / rules/ | 模板、角色、共用纪律与写法，记录实际版本和指纹 |

模块不自建向量服务、不依赖旧插件。未来海报等产物可复用材料、事实卡、规则和校验，另接模板与呈现适配器。

## 规划与确认

1. `outline action=preview` 仅检查模板；`action=plan` 宏观取材并保存 `outline-plan.json`。
2. 规划按作者身份、领域、目标和读者展开，代表证据最多四条；长内容先分批提取。只给粗目录、每章目的、查询方向和少量能力→场景→问题→趋势主线。
3. `action=confirm` 校验指定 SHA-256，记录 `confirmedAt/confirmedSha256`。用户确认意图由对话入口负责，工具参数不能证明真人审批。
4. `generate` 校验规划已确认、文档哈希与规则指纹，以及项目/导入/模板/目录/读者/作者/目标一致性。任何改动重新规划确认，不在正文阶段重跑详细规划。
5. 规划失败直接保留错误，不自动跳到正文；旧“只有模板预览就 generate”的调用方式需迁移。

当前确认是工作区内的本地文件协议，尚无平台多人审批、不可变知识文档版本或乐观锁。

## 证据与上下文

- 准备阶段核对项目可见绑定库及完成文档。统一 `/retrieval/query` 首期只接 hybrid，显式过滤完成文档，空列表不查询；404/405 才回退旧接口，权限错误不回退。
- 规划使用 `discover({light:true})`。正文仅 `forChapter`，每章选择最多八条远程命中与必要锚点；有远程命中时不叠加本地副本，无命中时可选本地相关窗口。
- 后台每次召回 top_k=12；全部已召回原文存档，不等于全部进入模型。条数及词面选择可能漏召回，无法证明全库覆盖。
- 原文窗口约 2400 字符、重叠 160 字符，每批约 6000 字符，所有选定窗口处理到末尾。字符值用于组织批次，不是 token 估算或总输入上限。机器校验始终用原文登记。
- 事实卡保留来源 ID 与短逐字引文；撰写只输入本批事实卡、必要原文及相关主线与规则，不重复全集。事实卡是派生内容，不能当成新来源；引文合法也不能自动证明概括准确。
- 补查最多一轮，只处理新增且按内容去重的证据，保留首次事实卡。记录问题、新证据及新事实数，不能把新增数量当成补查成功证明。
- 超时、上下文超限、输出耗尽只拆失败批，最多两层；无法拆再明确失败。临时/格式问题仅一次局部重试。原文、部分事实、分批草稿和错误分开保存。
- Wiki/图谱、后台父块/邻块回读、公开检索仍未接入。附近 180 字符的引文条件选段和本地窗口可能不足以解释长距离条件，人工需核对边界。

## 全章并行和模型调用

`generation.js` 一次提交所有章任务，章内按取证→提取→必要补查→分批写作顺序执行；各章不等其他章取证。模型流调用进程内共享默认八路（1–12 可配），检索共享四路；更多章可以进行独立准备或等待额度，不无限并发请求。

每个规划或生成运行固定 provider/model。DSH 提供精确模型能力查询时，选择声明支持的低档；不继承会话 high/max。缺查询或低档不可用时记录限制并使用提供方默认值，不能保证思考已经下降。低档由本机 DSH 接口适配，具体网关执行须真实验收。

输出预算及观测字段见 README。执行超时从获得额度后开始，排队默认 30 分钟、执行默认 10 分钟，独立计时；配置可按阶段覆盖。请求结束原因、输出预算、正文/思考字符及可得 usage 分开记录，不能把字符数当 token。

取消信号约束排队和执行；运行内写盘依序保存快照。已有材料和成稿保留，尚无跨进程自动恢复或单章重新生成工具。

## 必经合稿检查与修正

稳定编号的共享主线用于统一方向，各章仍独立找事实证据。客户问题无证据保持典型假设，不能从产品功能推成客户既有事实。业务现状/需求挑战与两类趋势框架各二选一，近义标题不改变 key/roleId。

`review.js` 每段进入章节分批检查；每个业务问题、趋势、场景段再寻找跨章候选，即使没有共享 ID。候选按 ID 和词面排序、每个目标角色选一个，短索引只导航；有限候选不能证明不存在其他关联。自定义角色完成逐段检查，但新的跨章语义角色需扩展目标映射。

五项必检为问题方案、能力证据、场景全景、趋势建设、矛盾与孤立内容。要求返回每项状态与理由；缺项视作未完成。涉及的重点关系不能用“不适用”绕过；关联分组超限拆分后保留子批检查，但联合语义未完成，不算通过。

有具体问题最多一轮局部修正，最多三个组、每组两段；保留段落编号和原稿，禁止范围外修改、删除或候选升级。更改后对最终合稿重新做全部检查，避免修好一处破坏另一处。修正失败保留原稿及问题。

`consistency-review.json` 和 `report.json.assemblyReview` 分别记录检查完成状态与是否通过；缺章不能整体通过。模型检查通过仍不是事实或业务语义的自动证明，最终报告保持待人工审阅。第一批保留小范围单轮全景追加；较大输入跳过独立追加并转入上述检查。
